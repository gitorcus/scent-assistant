# Security and untrusted-input review

Reviewed `v1.2.3-beta.1`, commit `ac928a73c3bed22cd00d5e5d875c6ff72445ab06`, against stable `v1.2.2`. This is a source review with synthetic offline probes, not physical BLE acceptance or a penetration test of the vendor service. No integration files, credentials, Home Assistant instance, or devices were changed. All identifiers and credentials in the probes are invented fixtures.

The most serious confirmed issue is the cloud client's disabled TLS certificate verification. The most immediate reporting risk is that a downloaded diagnostics file can disclose a configured GW password despite its structured password field being redacted. These are pre-existing defects, not regressions introduced by this beta. The beta adds a new path that treats invalid power/status bytes as an authoritative stopped state; this matters to the proposed fresh-response verification contract.

## Confirmed findings

### SEC-1 — High / P1: Cloud login and control disable TLS authentication

- **Plan status:** Item #10 is active approved remediation, no longer deferred; the defect remains unfixed. The [approved requirement](certificate-trust.md#approved-requirement-trust-once-renew-automatically) is explicit initial CA approval when needed, persistent endpoint-scoped trust, automatic valid renewals and authenticated CA transitions, plus distinct Reload trust and Review and re-pin actions. Ordinary renewal must not require repeated user approval. This updates the plan only, not runtime code or production trust.
- **Source:** `custom_components/scent_assistant/protocol_cloud.py:100-118`, `158-170`, `214-218`, `247-252`, `279-283`, `317-321`, `416-424`; HTTPS endpoints are declared at `const.py:403-404`.
- **Trigger and preconditions:** The user configures cloud access, and an attacker can intercept or redirect the HA host's traffic to the vendor endpoint, for example through an untrusted network or compromised local gateway/DNS. The attacker can present an untrusted TLS certificate because every request explicitly passes `ssl=False`.
- **Impact:** Interception of the reusable password hash and authentication response, theft of the cloud token, and modification of status/control traffic. After token login succeeds, `_web_login` first submits the original password in its form. An active interceptor can therefore recover the original account password too; hashing the earlier request does not contain the exposure. This is an active-interception risk, not a claim that passive observers can decrypt normally established TLS traffic.
- **Evidence:** The offline probe calls the actual `login()` method with a recording fake HTTP boundary: all resulting requests set `ssl=False`; the second request contains the synthetic original password. This confirms the certificate-verification bypass in source. The fake boundary does not test a live certificate, the actual HA runtime's trust store, or vendor login.
- **Scope:** `protocol_cloud.py` is unchanged between `v1.2.2` and this beta.
- **Unverified cause and compatibility:** Verification may have been disabled to work around a CA unavailable to the HA runtime, an incomplete chain, or another certificate-validation failure. The reason is unverified. No claim is made that the vendor's current chain is valid, that HA currently trusts it, or that removing `ssl=False` alone preserves cloud functionality. A successful certificate check on a reviewer's computer would not establish trust in the actual HA environment.
- **Required remediation investigation:** Before changing behavior, reproduce certificate validation using the actual supported HA runtime/session and trust store without submitting account credentials. Diagnose hostname/SAN matching, certificate expiry and runtime clock, intermediate-chain delivery, trusted root availability, and any private/custom CA or local TLS interception. Identify the platform-supported, narrowly scoped trust configuration if additional trust is necessary; verify the intended trust anchor rather than importing arbitrary presented certificates or weakening global verification. Fix a vendor-delivered chain at its source where appropriate.
- **Correction and acceptance:** Restore authenticated TLS through the supported session/trust mechanism established by that investigation, with actionable validation failures. Require both a valid intended chain/hostname success test and invalid/untrusted chain, wrong-hostname, and expired-certificate rejection tests. Then verify compatibility of the cloud workflow through a separately authorized runtime test, with credentials excluded from logs and artifacts. Do not blindly flip the flag or treat a new connection failure as an acceptable complete fix. Review redirects of credential-bearing requests and retain credentials only on the intended HTTPS origin.

### SEC-2 — Medium / P2: Downloaded diagnostics reveal a configured GW password in raw commands

- **Source:** `device.py:470-474`, `575-595`; `protocol_ble.py:1781-1795`; `diagnostics.py:24-27`, `79-81`, `102-103`.
- **Trigger and preconditions:** A password-protected GW integration sends its configured password during connection, the password frame remains among the last ten commands, and a user downloads/shares diagnostics. A recipient can decode the exported hex without access to HA's credential storage. Use of the password against a diffuser additionally requires reachability of that diffuser's BLE service.
- **Impact:** Disclosure of the user-specified four-character GW password. `_ble_send()` saves the complete logical password frame before transport chunking; diagnostics exports the buffer verbatim. Redacting `entry.data.gw_password` does not redact the encoded occurrence.
- **Evidence:** Executing actual `build_password()`, `_ble_send()`, and diagnostics export with a synthetic `Q7x9` fixture produces command hex `ff01000daf0005c051377839`, while the structured password field is redacted. `bytes.fromhex(...)` recovers the fixture. Only the HA redaction helper and transport are stubbed; the command recording and diagnostics field selection are actual source.
- **Scope:** Pre-existing in stable `v1.2.2`; this beta only adds timestamp/refresh fields to diagnostics. This is an integration export defect, distinct from the known vendor protocol's limited password strength.
- **Minimal correction:** Classify authentication frames before recording them and exclude or sanitize their payloads. Sanitize both outgoing and incoming diagnostic captures, because a peer could echo an authentication frame. Add a regression check that exported JSON contains neither a synthetic secret nor its wire encodings. Do not automatically change device credentials as part of this fix.

### SEC-3 — Medium / P2: Debug logging serializes the cloud access token

- **Source:** `protocol_cloud.py:169-181`, additionally `120-121` for unrestricted web-login response logging.
- **Trigger and preconditions:** Debug logging for the integration is enabled during cloud login, and another party receives the debug log or otherwise has access to it. Debug logging is not required for ordinary use, so this is conditional exposure.
- **Impact:** The successful authentication response is logged before `data.accessToken`, `data.access_token`, or `data.token` is extracted. Thus log disclosure includes a bearer credential for the vendor account, within whatever scope/lifetime the vendor grants that token. No account-scope or token-lifetime assumption was tested. The unrestricted web response log can expose additional auth material if the vendor includes it there.
- **Evidence:** The synthetic offline successful login writes `SYNTHETIC_ACCESS_TOKEN` into a captured DEBUG log stream.
- **Scope:** Pre-existing; cloud source is identical to stable `v1.2.2`.
- **Minimal correction:** Log a small allowlist such as HTTP/result code and presence of expected fields. Never log complete authentication responses; error responses need the same discipline because they may echo input or tokens. A diagnostics-only redactor cannot protect logger output.

### SEC-4 — Low / P3: Diagnostics' MAC redaction is defeated by raw advertisement hex

- **Source:** `protocol_ble.py:2214-2222`, `2236-2237`; `diagnostics.py:24-27`, `79-81`, `97-103`.
- **Trigger and preconditions:** A supported advertisement embeds a MAC, and the user shares diagnostics. `mac_from_adv` is extracted from `raw_hex`; diagnostics redacts the extracted field while retaining the original source bytes in metadata.
- **Impact:** A stable device identifier remains recoverable from an ostensibly redacted diagnostic export. It is a privacy/correlation issue, not an authentication bypass. Raw notifications can also contain identifiers: the Aroma-Link work-info layout explicitly places a MAC at payload offsets 22-27 (`protocol_ble.py:547`), and recent notifications are exported unchanged. Titles, configured BLE names, device names, and labels also remain; these may contain user-chosen location/person information.
- **Evidence:** The synthetic advertisement probe shows `mac_from_adv` redacted while the exact synthetic MAC remains a substring of exported `raw_hex`.
- **Scope:** Pre-existing metadata redaction defect. The beta's recurring Aroma-Link polling can make raw work-info notifications more routinely present, but did not introduce raw notification export.
- **Minimal correction:** Redact encoded identifier regions or omit raw captures from default diagnostics. Apply an explicit privacy schema to the complete export, including title, names, labels, entry data and options. If packet-level captures remain necessary, make their additional disclosure clear and narrowly opt-in; do not describe them as already sanitized.

### SEC-5 — Medium / P2: GW transport reassembly has no size bound or sequence/session validation

- **Source:** `protocol_ble.py:1847-1865`; related lifecycle `device.py:499-534`.
- **Trigger and preconditions:** A selected/connected GW or GW-XOR peripheral emits repeated full-size notifications without a terminating short chunk, whether from a device fault or a malicious peripheral that HA has connected to. This is not reachable merely by sending unrelated advertisements. The ten-second normal idle disconnect limits one connection, but the protocol object's buffer is not cleared by the teardown shown here, so accumulation can survive successive sessions.
- **Impact:** Every chunk appends another retained bytes object. Nonce and sequence bytes are discarded without checks, so duplicate/out-of-order chunks also accumulate. Sustained/repeated delivery can consume unbounded process memory; a late terminator joins the entire buffer at once and can produce a large allocation or parse a mixed frame. The test demonstrates unbounded retention, not exhaustion of a real HA host.
- **Evidence:** The actual parser retains 10,000 identical `(nonce=1, sequence=1)` full chunks, totaling 180,000 payload bytes plus Python list/object overhead. No reset or limit occurs. GW-XOR inherits the same reassembler.
- **Scope:** Pre-existing. Aroma-Link's new `AL_RX_BUFFER_MAX = 512` is a useful beta mitigation for a different protocol and does not protect GW.
- **Minimal correction:** Bound per-frame bytes/chunks, enforce an expected nonce/sequence progression, expire incomplete frames, and reset transport state on disconnect/new session. Drop malformed/truncated frames before decoding any state. Limits must match verified protocol maximums rather than borrow a different family's limit.

### SEC-6 — Medium / P2: Recognized BLE state fields accept invalid types or escape parser errors

- **Source:** Scentiment `protocol_ble.py:845-852`, `875-896`; GW-XOR `2087-2097`, `2120-2128`; cache application `device.py:626-685`.
- **Trigger and preconditions:** A faulty or attacker-controlled connected peripheral sends syntactically valid JSON with invalid values. The threat boundary is the connected BLE peer; there is no demonstrated remote-network entry point.
- **Impact:** Scentiment copies arbitrary JSON keys/values and the device manager copies recognized fields into cache. For example, `{"power":"off","battery":999,"start_hour":99,"level":{}}` becomes state updates unchanged. A truthy string can misrepresent power, invalid clock fields can fail time rendering, and inappropriate types can break calculations. GW-XOR's `int(value)` for power/lock occurs outside its decrypt/JSON exception handler, so `{"1":{"value":"n/a"}}` (DP 1) raises `ValueError` through `_on_ble_notification()`. This interrupts processing of that notification; it is not evidence that the HA process crashes.
- **Evidence:** The offline probes execute both actual parsers and observe those exact accepted Scentiment values and the escaped GW-XOR exception.
- **Scope:** Pre-existing in stable `v1.2.2`.
- **Minimal correction:** Introduce protocol-specific field allowlists, exact type/range/enum validation, and a safe parser boundary before updating caches or invoking entity callbacks. Preserve the last valid value, mark invalid/stale evidence explicitly, and prevent invalid data from satisfying any proposed Ready to Serve verification. Do not solve invalid readings merely by coercing arbitrary types or clamping them into plausible values.

### SEC-7 — Medium / P2: New Aroma-Link status path converts invalid bytes into verified-looking off state

- **Source:** `protocol_ble.py:383-391`, `555-558`; state application/freshness `device.py:631-633`, `725-729`.
- **Trigger and preconditions:** An Aroma-Link peer sends a checksum-valid all-work-info response with invalid on/off and work-status bytes, such as `0xFF, 0xFF`. Ordinary corruption that invalidates the checksum is a different case; checksums alone do not validate field meaning.
- **Impact:** The new code interprets any power byte other than `1` as `False`; `_phase_from_status` then labels it `off`. The device manager accepts the result and advances the BLE last-update timestamp. This can display a fresh stopped state when the response is invalid. The current beta has no RTS verifier, so the finding must not be described as an already exploited RTS success; it identifies a concrete blocker to using these fields as the approved valid-response proof.
- **Evidence:** An actual `_build_packet()`/`parse_notification()` round trip with these invalid bytes returns `{"power": false, "phase": "off"}`.
- **Scope:** This all-work-info power/phase handling is introduced in `v1.2.3-beta.1`. Older dedicated power paths have similar weak enum handling; the entire invalid-value problem is not new. The beta's new work-frequency parser also treats any nonzero enable nibble as true (`613`), which deserves protocol-verified enum checks.
- **Minimal correction:** Reject values outside each field's verified wire enum before state/freshness advancement. Record invalid-response evidence separately and retain prior valid field values. Apply validation consistently across status, query, and schedule paths.

## Auth/configuration and dependency/CI observations

These are hardening recommendations or compatibility observations, not evidence of exploitation or malicious dependencies.

- **Vendor BLE limitations:** AK uses the documented fixed login sequence/PIN; GW supports a four-ASCII-character password; GW-XOR uses vendor-compatible obfuscation based on a public table/MAC. These are known protocol constraints and must not be reclassified as newly introduced integration cryptography bugs. Nearby-device trust remains relevant. No credential-change action was attempted or proposed as an approved operation.
- **Password input validation:** `config_flow.py:68-70` silently truncates a supplied GW password and permits non-ASCII text; `protocol_ble.py:1788` later encodes strict ASCII, and `device.py:473-476` suppresses the resulting error. Reject invalid length/charset during configuration and surface an actionable authentication error rather than silently accepting unusable input. Password fields are plain `str` schemas (`config_flow.py:75`, `224`); verify that the HA form actually masks them and use an explicit password selector if necessary. No claim about rendered form masking was made without rendering HA.
- **Credential storage:** Cloud credentials and optional GW password are stored in HA config-entry data (`config_flow.py:56-57`, `246-252`). This is conventional HA storage, not independently an access-control bypass. Protect normal HA backups/configuration and ensure diagnostics do not leak derived forms of those values. The reviewed integration adds no public HTTP endpoint or custom unauthenticated administrative route.
- **Remote response hardening:** Cloud responses are read in full and parsed with `content_type=None`; broad exception handling usually returns a failure. Set an appropriate response-size bound and validate response structure/result codes before using state. `set_power()` returns true on any HTTP 200 (`protocol_cloud.py:254-261`), even a vendor error body; this is a command-result correctness defect, not proof of an auth bypass, and belongs in the main behavior review.
- **Mutable CI code:** `.github/workflows/hacs.yaml:15-16` runs `actions/checkout@v4` and `hacs/action@main`; `.github/workflows/hassfest.yaml:15-16` runs `actions/checkout@v4` and `home-assistant/actions/hassfest@master`. Pin reviewed action revisions and maintain them with an update workflow. Both workflows omit explicit `permissions`; set `contents: read` or the minimal demonstrated permissions. Actual effective token privileges depend on repository settings and were not inferred from the omission. No `pull_request_target`, explicit secret injection, or release/upload job is present in these two workflows.
- **Floating dependencies:** `manifest.json:21` specifies lower bounds (`bleak>=0.21.0`, `bleak-retry-connector>=3.0.0`) without a reproducible upper/pinned resolution. New installations may resolve different versions; test/document the supported HA dependency combination and follow HA requirements policy for reproducible installation. This is not evidence that an installed dependency has a CVE. Dependency advisory/scanner and live CI results are separate root-review evidence.
- **Packaging:** Manifest version matches the reviewed beta tag; source consists of integration Python/configuration and brand assets, with no repository-owned installer/download-execute hook or vendored executable found. HACS/hassfest workflows validate metadata, not the runtime BLE security boundary. Passing them cannot establish that the findings above are absent.

## Offline reproduction and limits

`python3 -B tools/beta-review/security.py` executes the exact checked-out source through stubbed BLE/HA/HTTP boundaries. It asserts no physical result and obtains no external credentials. Observed outputs: original synthetic password present in cloud web-login form; TLS verification false; synthetic token present in DEBUG log; structured password redacted but raw command recoverable; raw advertisement identifier recoverable; GW retained 10,000 chunks / 180,000 payload bytes; Scentiment invalid values preserved; GW-XOR `ValueError`; beta invalid status becomes off.

The source checkout remained unchanged. No active account tests, TLS interception, BLE spoofing, physical cutoff tests, private logs, or external dependency exploit probes were performed. The actual HA trust store, vendor certificate chain, and compatibility of a validating replacement session remain untested. The confirmed TLS bypass and the unverified reason for that workaround are separate conclusions. Findings about cloud authentication and public diagnostics should be addressed before broadly recommending the affected workflows; a BLE-only rollout does not exercise the cloud issue, but does not fix it for cloud users.

## Maintainer/Claude handoff requirement for SEC-1

Treat the missing-CA explanation as a plausible compatibility constraint to investigate, not an established cause or a reason to dismiss the confirmed verification bypass. Do not change `ssl=False` as an isolated cleanup. First identify the actual HA runtime's certificate-validation failure, including hostname, expiry/time, intermediates, root trust, and private/custom CA conditions. Propose the platform-supported scoped trust/session configuration and demonstrate valid-chain success plus invalid-chain failure. A public endpoint chain inspection or a test on a different machine cannot substitute for HA runtime evidence. Keep this work separate from device-credential changes, which are not authorized by this review.
